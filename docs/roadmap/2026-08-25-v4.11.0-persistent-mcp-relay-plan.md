# lnwjud v4.11.0 — Persistent MCP Relay Plan

Status: **planned / development branch**  
Target branch: `dev`  
Date: 2026-08-25  
Primary goal: **Transport may disconnect; the logical MCP Profile must survive.**

## 1. Problem statement

lnwjud v4.10.0 already has strong local execution resilience: an application-global loopback HTTP MCP, Secure Tunnel auto-reconnect, a 168-hour configured MCP connection ceiling, durable background tasks, shared SQLite state, multi-workspace/session attribution, recovery/checkpoints, and session handoff.

The remaining gap is one layer above the local runtime. Today the remote identity is still too close to the lifetime of the OpenAI Secure MCP Tunnel/client connection. A tunnel or Desktop restart can recover the local MCP runtime, but the AI-side connector can still need a reconnect/refresh when the remote transport identity or cached tool state becomes stale.

The v4.11.0 objective is to introduce a stable remote profile identity in front of the existing local MCP runtime without rewriting the existing tool registry.

## 2. Non-goals for v4.11.0

Do **not** bundle the following into the first relay release:

- multi-device automatic failover;
- full web fleet console;
- mandatory lnwjud cloud account;
- billing/licensing;
- team/RBAC;
- macOS/Linux capability parity;
- remote storage of file contents, commands, screenshots, work logs, or tool output;
- removal of OpenAI Secure Tunnel support.

Those are follow-up work after connection continuity is proven.

## 3. Product invariant

The product must separate three lifecycles that are currently easy to confuse:

```text
Public MCP Profile lifetime    ███████████████████████████████████
Desktop relay connection       ███████   █████████   █████████████
Local MCP runtime              █████████████  █████████████████████
Durable tool/task execution    ███████████████████████████████████
```

A relay transport disconnect must not imply local MCP death, and local MCP restart must not change the public MCP profile URL.

## 6. Task 1 — Relay protocol and Desktop worker agent

### Deliverables

- profile/device/connection identifiers;
- authenticated outbound worker connection;
- heartbeat every approximately 5 seconds;
- device lease approximately 20 seconds;
- monotonically increasing connection epoch;
- reconnect state machine with bounded exponential backoff and jitter;
- explicit states: `disconnected`, `connecting`, `authenticating`, `connected`, `reconnecting`, `disabled`, `error`;
- relay disconnect never restarts local MCP automatically.

### Reconnect baseline

```text
250 ms -> 500 ms -> 1 s -> 2 s -> 4 s -> 8 s -> 15 s max + jitter
```

### Acceptance

- stop the relay socket without stopping Desktop: local MCP stays running;
- restore connectivity: worker reconnects automatically with a new epoch;
- stale epoch frames are rejected;
- Desktop restart reconnects using the same device/profile identity.

## 7. Task 2 — Persistent public MCP profile endpoint

### Profile model

```text
profile_id
profile_name
public_mcp_path
active_device_id
auth_policy
catalog_version
catalog_hash
created_at
updated_at
```

### Device/lease model

```text
device_id
profile_id
connection_id
connection_epoch
lease_expires_at
last_heartbeat
runtime_version
catalog_hash
```

### Rules

- the URL identifies the profile, not a process;
- restarting Desktop does not change the URL;
- the public profile can remain addressable while the active worker is offline;
- a single active device is enough for v4.11.0; multi-device switching is deferred.

### Acceptance

Configure an AI client once, restart lnwjud, reconnect the worker, and use the same profile endpoint without editing the connector URL.

## 8. Task 3 — Request journal and effectively-once execution

A relay introduces a distributed-systems failure mode: execution can complete locally while the connection dies before the result reaches the caller. Automatic replay must not duplicate side effects.

### Required request envelope

```text
request_id
idempotency_key
profile_id
device_id
connection_epoch
deadline
tool_name
input_hash
```

### Local request journal states

```text
RECEIVED
DISPATCHED
RESULT_COMMITTED
DELIVERED
FAILED_TERMINAL
```

### Replay classes

| Class | Examples | Reconnect behavior |
| --- | --- | --- |
| Safe read | `read_file`, `search_text`, `git_status` | safe retry |
| Idempotent write | deterministic same-content write | same request/idempotency key only |
| Managed execution | `shell`, `process_start` | recover existing task/execution handle |
| Non-idempotent/destructive | delete/discard/send-type effects | never auto-execute a second time after committed receipt |

### Rules

- duplicate `request_id` + same `input_hash` returns committed/cached result;
- duplicate `request_id` + different input is a protocol error;
- destructive requests must have an execution receipt before result delivery;
- result payload caching is bounded and may reference a local durable result rather than copying unlimited output into the relay database;
- cloud relay must not become the primary repository of command/file payloads.

### Acceptance

Simulate disconnect after local commit but before response delivery. Reconnect and resend the same request. The mutation must execute once and the prior result/receipt must be returned.

## 9. Task 4 — Stable/versioned tool catalog

The public profile should expose a catalog identity independent of an individual Desktop connection.

### Catalog state

```text
catalog_version
catalog_hash
runtime_version
tools[]
updated_at
```

### Behavior

- worker sends catalog hash during HELLO;
- unchanged hash leaves the public catalog untouched;
- changed catalog is validated, then swapped atomically;
- Desktop disconnect does not erase `tools/list`;
- profile may continue to expose the last validated catalog while marking the worker offline;
- incompatible catalog changes need an explicit compatibility policy rather than silently breaking old clients.

### Acceptance

- restart Desktop with the same catalog: tools remain stable;
- upgrade runtime with a compatible catalog: endpoint remains unchanged;
- invalid/partial catalog update: retain prior validated catalog.

## 10. Task 5 — Offline/reconnect facade

The profile endpoint must distinguish `profile exists` from `worker currently reachable`.

During a short reconnect grace window (default proposal: 30 seconds), an interactive call can wait for the worker to return. When the worker is offline beyond the grace window, the profile endpoint remains valid and returns a typed retryable error such as:

```json
{
  "code": "DEVICE_OFFLINE",
  "retryable": true,
  "last_seen_seconds": 42
}
```

During reconnect:

```json
{
  "code": "DEVICE_RECONNECTING",
  "retryable": true,
  "grace_seconds": 30
}
```

The endpoint itself must not disappear merely because Desktop is offline.

## 13. Protocol compatibility

The existing HTTP MCP implementation already contains modern and legacy handling. Do not remove compatibility solely to build the relay.

The relay should be designed so that public protocol compatibility is isolated from local tool execution. Newer stateless MCP behavior can route requests independently; older session-oriented clients can be represented by a compatibility facade at the relay boundary.

Protocol/version negotiation must be covered by contract tests before enabling a protocol version in production.

## 14. Security requirements

- worker connection is outbound-only by default;
- no public inbound listener is required on the Windows machine;
- public endpoint requires authentication unless an explicitly documented development-only mode is selected;
- profile credentials and worker credentials are distinct;
- device credentials are revocable and rotatable;
- relay server cannot bypass the local lnwjud permission engine;
- Active Project, Full/Safe/Balanced profile semantics, Protected Critical Files, Recovery Trash, and destructive confirmation remain enforced locally;
- request envelopes have bounded sizes and deadlines;
- stale connection epochs cannot authorize work;
- duplicate destructive request IDs cannot repeat committed effects;
- secrets never appear in relay logs;
- all relay metadata logs are bounded and redacted.

## 15. Chaos / E2E acceptance matrix

### A. Desktop restart

1. AI client remains configured to the same URL.
2. Restart lnwjud Desktop/runtime.
3. Worker reconnects.
4. New tool call succeeds without editing the URL or refreshing connector configuration.

### B. 10-second network outage

1. Disconnect network/relay channel for 10 seconds.
2. Local MCP remains alive.
3. Restore network.
4. Worker reconnects inside grace/backoff budget.
5. Same profile URL resumes service.

### C. Read interrupted in flight

A safe read can be retried or result-replayed without user-visible connector replacement.

### D. Destructive call result lost after commit

The same request ID must not execute twice.

### E. Durable background task

Start a long `shell` task, disconnect the relay, reconnect, then retrieve the same durable task result by ID.

### F. Desktop offline

`tools/list` remains available from the last validated catalog; tool execution returns typed `DEVICE_OFFLINE` rather than making the profile cease to exist.

### G. Catalog upgrade

Compatible catalog update is atomic; an invalid catalog never replaces the prior good catalog.

### H. Security

Expired/revoked device token, stale epoch, invalid profile token, oversized frame, mismatched request hash, and replayed destructive request are all rejected deterministically.

## 16. Implementation phases

### Phase 0 — Design spike

- freeze relay message schemas;
- select worker transport (WebSocket is acceptable for the spike; keep protocol transport-neutral where possible);
- build an in-memory relay fixture;
- prove Desktop -> relay -> loopback HTTP MCP -> relay result round trip.

Exit criterion: one existing read-only tool works through the relay without changing the tool registry.

### Phase 1 — Persistent identity

- profile/device identity;
- stable URL route;
- outbound worker connection;
- heartbeat/lease/epoch;
- reconnect state machine.

Exit criterion: Desktop restart does not require changing the profile URL.

### Phase 2 — Reliability journal

- SQLite request journal;
- idempotency/replay policy;
- result receipt/recovery;
- durable task integration.

Exit criterion: disconnect-after-commit test cannot duplicate a mutation.

### Phase 3 — Catalog/offline facade

- versioned catalog;
- offline/reconnecting typed state;
- reconnect grace;
- compatibility tests.

Exit criterion: profile remains addressable while Desktop is offline.

### Phase 4 — Self-host packaging and UI

- relay-server package/container;
- self-host configuration;
- Desktop setup UI;
- health/Doctor integration;
- documentation.

Exit criterion: another user can deploy the relay without lnwjud-operated cloud infrastructure.

### Phase 5 — Release hardening

- chaos tests;
- clean-machine install;
- upgrade/rollback tests;
- security review;
- metrics/redaction review;
- installer packaging.

## 18. Definition of done for v4.11.0

v4.11.0 is not considered successful merely because a relay socket stays connected for hours. It is successful when all of the following are true:

- public profile URL is stable across Desktop restarts;
- short network loss is transparent to profile identity;
- local MCP and durable tasks continue independently of relay transport;
- duplicate/replayed requests cannot duplicate destructive effects;
- tool catalog survives worker disconnect;
- self-host deployment works without mandatory lnwjud cloud;
- OpenAI Secure Tunnel still works as a fallback;
- existing local permission/recovery boundaries remain authoritative.

The final product requirement is therefore:

> **Connection can drop. User work and MCP profile identity must not drop with it.**
